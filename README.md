# Лабораторна робота №3 — REST API з SQLite

**Варіант: Сервіс реєстрації на факультатив/подію** Бекенд-система для автоматизації запису студентів на додаткові заняття та заходи, що дозволяє керувати списком подій, базою користувачів та відстежувати реєстрації в режимі реального часу.

## Як запустити проєкт

1. **Встановіть залежності:**
   ```bash
   npm install
   ```

2. **Запустіть сервер у режимі розробки:**
   ```bash
   npm run dev
   ```

**Порт за замовчуванням:** Сервер запуститься на [http://localhost:3000](http://localhost:3000)

## База даних та ініціалізація

* **СУБД:** SQLite.
* **Файл бази:** Автоматично створюється за шляхом `data/app.db`.
* **Схема:** Таблиці створюються автоматично при першому старті за допомогою SQL-команд `.
* **Seed (Тестові дані):** Реалізовано механізм автоматичного наповнення бази. Якщо таблиця користувачів порожня, система додає тестові записи для користувачів, подій та реєстрацій для демонстрації зв'язків.

## Схема БД (Структура)

В системі реалізовано 3 взаємопов'язані сутності:

1.  **Users (Користувачі):** `id`, `name`, `email` (unique).
2.  **Events (Події):** `id`, `title`, `date`, `location`, `capacity`, `description`.
3.  **Registrations (Реєстрації):** `id`, `eventId`, `userId`, `registeredAt`.
    * **Зв'язок:** `FOREIGN KEY (eventId) REFERENCES Events(id) ON DELETE CASCADE`.
    * **Зв'язок:** `FOREIGN KEY (userId) REFERENCES Users(id) ON DELETE CASCADE`.
    * **Обмеження:** `UNIQUE(eventId, userId)` — один користувач не може зареєструватися на ту саму подію двічі.

## Приклади запитів (cURL)

### 1. Отримати всі реєстрації (3-тя сутність з JOIN)
Демонстрація отримання даних із пов'язаних таблиць (ім'я користувача + назва події):
```bash
curl -i http://localhost:3000/api/registrations
```

### 2. Складний запит (WHERE + ORDER BY + LIMIT)
Приклад отримання подій у конкретній локації із сортуванням за датою:
```bash
curl -i "http://localhost:3000/api/events?location=Aud.315&sort=date&order=desc&limit=5"
```

### 3. Створити нову реєстрацію (Успіх - 201 Created)
```bash
curl -i -X POST http://localhost:3000/api/registrations -H "Content-Type: application/json" -d "{\"eventId\": 1, \"userId\": 1}"
```

### 4. Отримати користувача за ID
```bash
curl -i http://localhost:3000/api/users/1
```

## Технічні особливості

* **Повний CRUD:** Реалізовано асинхронні методи `POST`, `GET` (list/id), `PUT` та `DELETE` для всіх сутностей.
* **Централізована обробка помилок:** Middleware перетворює SQL-помилки у зрозумілі відповіді: `409 Conflict` для дублікатів та `400 Bad Request` для неіснуючих ID.
* **Логування:** Сервер фіксує кожен запит та ключові події БД (відкриття файлу, ініціалізація схеми).
* **Безпека:** Додано файл `.gitignore` для запобігання завантаженню локальної бази даних у репозиторій.

## Опис проєкту
Вебдодаток для керування реєстрацією студентів на факультети та події. Проєкт реалізований за архітектурою Full Stack та складається з двох частин:

## Що реалізовано 

* **Реалізація CRUD:** Повна підтримка створення, читання, оновлення та видалення записів (реєстрацій) через REST API.
* **Модульна архітектура:** Код клієнта розділено на логічні шари: `apiClient.js` (мережевий прошарок), `ui.js` (DOM-маніпуляції) та `main.js` (керування бізнес-логікою).
* **Централізована обробка станів:** Інтерфейс автоматично обробляє стани `loading`, `empty`, `success` та `error`, забезпечуючи користувачеві зрозумілий зворотний зв'язок.

* **Обробка помилок:** Реалізовано механізм перехоплення мережевих помилок (включаючи таймаути та CORS-блокування), що повертає інформативні повідомлення замість технічних відмов браузера.

### Сценарій А: Захист від SQL-ін'єкції (SQLi)
* **Як відтворити:**Виконати GET-запит /api/v1/events?sort=id' OR 1=1. Через конкатенацію змінної сортування у запит, вразлива система ламає синтаксис SQLite і повертає критичну помилку бази даних (500 Internal Server Error).
* **Як виправлено:** Замінено небезпечну конкатенацію. Для параметрів сортування (ORDER BY) впроваджено строгий білий список (Allowlist). Для фільтрації (наприклад, за локацією) застосовано параметризовані запити з використанням плейсхолдерів ? та масивів параметрів.
* **Як перевірити:** Повторний запит із тим самим payload обробляється безпечно — бекенд відкидає невідомий параметр, підставляє безпечне сортування за замовчуванням і повертає статус 200 OK зі списком подій.
  
### Сценарій Б: Захист від міжсайтового скриптингу (XSS)
* **Як відтворити:** Створити подію, вказавши в полі title (Назва події) значення <img src="x" onerror="alert('XSS')">. При відображенні таблиці подій через innerHTML браузер намагався завантажити зображення і виконував шкідливий JavaScript-код.
* **Як виправлено:** Виконано рефакторинг фронтенд-логіки рендерингу. Замість вставки сирого HTML застосовано створення DOM-вузлів через document.createElement та безпечне виведення тексту за допомогою властивості textContent.
* **Як перевірити:** Після створення аналогічної події тег <img> відображається в таблиці просто як звичайний текст, не викликаючи виконання коду.

### Сценарій В: Захист від IDOR (Broken Access Control)
* **Як відтворити:** Використовуючи HTTP-заголовок X-Demo-UserId: 2, зробити DELETE або GET запит до події, що належить іншому користувачу (наприклад, /api/v1/events/5, де власником є користувач 1). Сервер не перевіряв права власності та успішно видаляв або повертав чужий ресурс.
* **Як виправлено:** У бекенд-репозиторії до всіх чутливих методів (getById, update, delete) додано перевірку власника — умову AND ownerUserId = ?, де ідентифікатор береться з контексту авторизованого користувача.
* **Як перевірити:** Повторна спроба маніпуляції чужим ресурсом із тим самим заголовком тепер блокується системою і повертає помилку 404 Not Found (або 403 Forbidden). Доступ до власних подій залишається успішним.

### Сценарій Г: Security Misconfiguration
* **Як відтворити:** Запити до сервера повертали детальні `stack trace` у разі виникнення помилок, а в заголовках відповідей були відсутні вказівки щодо безпеки контенту.
* **Як виправлено:** Налаштовано централізований обробник помилок, що повертає клієнту лише стандартизоване повідомлення про помилку. Впроваджено middleware для додавання безпечних HTTP-заголовків (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`).
* **Як перевірити:** Аналіз `Response Headers` у вкладці `Network` DevTools підтверджує наявність встановлених заголовків безпеки, а при спробі викликати помилку сервер повертає чистий JSON без розкриття внутрішньої структури проекту.
